## Business Context
> **As a** system administrator of an edo deployment
> **I want to** the UI (vue-frontend and EdoClient) to distinguish the four roles guest / fellow / steward / admin with a single capability matrix
> **So that** read-only observers see everything but cannot mutate, contributors draft annotations, stewards confirm and publish, and only admins touch system diagnostics — consistently in both clients and mirrored by server-side enforcement

Created from the **vue-frontend uplift planning** (`frontend/vue-frontend/docs/uplift/PLAN.md`, **Phase 6**; specification `docs/uplift/SPEC-bounded-contexts-and-ui.md` §RBAC matrix). **Current state (verified):** the frontend has a three-value `AppMode` (`normal | debug | admin` in `lib/settings.ts`, used by the router `beforeEach` gate for `/transform` and `/databus`) — developer *modes*, not organizational *roles*. The AppBar already shows a mode badge with the placeholder title "RBAC roles arrive with uplift Phase 6" (Phase 0).

**Open decision (blocker PLAN §4 #4):** how roles travel to the frontend — socket-ux session, JWT/OIDC claim, or (interim) local settings? This card includes making that decision; the UI must not hard-code against an undecided transport.

---

## Plan

1. **Decide the role transport.** Options, in preference order: (a) socket-ux returns the resolved role with an authenticated request (session/header based, mirror of server-side enforcement); (b) OIDC/JWT claim carried by the infrastructure (regimo-infrastructure); (c) interim local setting (replaces `AppMode`, clearly labelled as not secured). Record the decision and the socket-ux contract in this card before implementation.
2. **Single capability map.** `frontend/vue-frontend/src/lib/capabilities.ts`: one map encoding the spec's RBAC matrix (read all views; trigger ADP sync → steward+; author CCA drafts → fellow+; accept CCA mappings → steward+; run SHACL checks → fellow+; deposit/publish → steward+; system diagnostics → admin). Views consume only this map — no scattered role checks.
3. **Roles replace modes in the shell.** `settings.ts`/auth plumbing switches from `AppMode` to the four roles; the router `beforeEach` becomes a role gate with an *explanatory* disabled/redirect state (tooltip or message naming the required role) instead of a silent redirect. The developer-only views (`/transform`, `/databus`) keep their mode-style gating as an orthogonal concern.
4. **Wire the known capability points.** The surfaces that already exist: manual sync trigger (ADP view — needs the socket-ux/core endpoint, PLAN §4 #5), SHACL runs and NovaCrate editing (FEP), bus/system diagnostics (Bus drawer / Databus view → admin/steward read-only). CCA acceptance points are added with Phase 3 ([[CF2-008]] domain work).
5. **Server-side is the real gate.** Every UI capability gated by a role must correspond to an enforced restriction in socket-ux (or the calling socket) — the UI matrix is UX, not security. Endpoints answer `403` with the required role.
6. **Qt parity.** The same matrix mirrored in `EdoClient` (role-based access control is already a stated Qt-client concept); implemented in the Qt repository, aligned here.

## Acceptance Criteria
- [ ] **Scenario:** Guest is read-only
	- **Given:** The UI session resolves to role `guest`
	- **When:** Any domain workspace is opened
	- **Then:** All mutation controls (sync trigger, editor mutations, deposit) are hidden or disabled with an explanatory tooltip; all read views render normally
- [ ] **Scenario:** Steward-only capability
	- **Given:** Role `fellow` with a project open
	- **When:** The ADP workspace is displayed
	- **Then:** The sync trigger is disabled with a tooltip naming the required role `steward`; with role `steward` it is enabled (once the trigger endpoint exists)
- [ ] **Scenario:** Server-side mirror
	- **Given:** A request attempting a steward-only operation
	- **When:** It is sent without steward privileges
	- **Then:** The backend answers `403` naming the required role — the UI gate is never the only enforcement
- [ ] **Scenario:** Single source of truth
	- **Given:** The capability matrix in `capabilities.ts`
	- **When:** A new domain view is added
	- **Then:** Its gating is expressed only through that map (grep proves no scattered `role ===` checks in views)
