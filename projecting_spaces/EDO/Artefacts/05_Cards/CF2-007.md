- [x] **Scenario:** hasContact conformance decided and consistent
	- **Given:** `edo:ProjectShape` demands ≥ 1 `edo:hasContact` (`sh:minCount 1`), but the maDMP export for project "Measurement_02" carries no `contact`
	- **When:** One of the decision options is implemented and propagated to all consumers that mirror the shape
	- **Then:** The SHACL stage passes (F1 closed) and the consistent choice is reflected in the shape, the internal-format spec, and `trip.py`/`agnostic_trip.py` if needed

## Decision options (choose one)
1. **Relax the shape** — set `sh:minCount 0` on `edo:hasContact` (contact optional, faithful P6 "omit"). Touches `shapes/project-claim-shapes.ttl` and the spec §3.2 / ERD.
2. **Guarantee contact in the (RDMO) export** — require a contact in the RDMO project; makes the source carry the data. Higher data-entry burden; may not hold for all projects.
3. **Derive a contact from a contributor** — fall back to the first contributor (or a `Contact Person`-type contribution) when `contact` is absent; synthesises a value rather than a faithful mapping.

**Decision (2026-11-23): option 2, realised as a candidate-list fallback in the exporter** — the maDMP export mapping's contact spec accepts a list of candidate base attributes (`project/data_management`, then `project/coordination`) and uses the first that answers. Projects created from a DOI without a dedicated DMP-contact question therefore still carry a contact (verified for project #11 → "Mohamed Anis Koubaa"). The shape stays at `sh:minCount 1`; faithful omission is retained only when **no** candidate answers (such projects would still trip F1 — accepted residual, see activity log).

> Open question to weigh: RO-Crate / OEP consumers may require a contact for their own validation — if so, "relax" only defers the problem to the downstream targets (see CF4-001).
