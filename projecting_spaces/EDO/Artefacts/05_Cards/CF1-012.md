## Business Context
> **As a** Researcher / UI user
> **I want to** see the Kafka databus messages (headers + payloads) of the EDO sockets in a suitable way in the user interface
> **So that** the ontology-aware bus becomes observable — which socket published what, when, with which provenance — without command-line tooling

Revisits [[CF1-001]] (Databus as a separated Kafka broker, closed 2026-11-18): the bus carries real payloads since then, but the browser cannot speak the Kafka wire protocol. The frontend already ships the display side — `frontend/vue-frontend/src/components/TheDatabus.vue` + `src/lib/databus.ts` (topic chips, 6-header-contract table, expandable messages with headers/payload JSON, demo fallback) — against a REST bridge contract that is explicitly marked **"backend — to be implemented"**. This card implements that backend in **socket-ux** and switches the UI from demo data to the real bus.

---

## Plan — socket-ux side (the `/bus` REST bridge)

1. **Reuse the existing consumer, add a ring buffer.** `events.py::BusSubscriber` already consumes `edo.projects.v1` in a background thread and fans events out through `EventBus` → SSE. Extend it to subscribe to all configured topics and, alongside the SSE fan-out, append every decoded message to a bounded per-topic `collections.deque(maxlen≈100)` enriched with `partition`, `offset` and broker timestamp. Rationale: Kafka has no native tail-N read; per-request consumer seeks are slow and unbounded; the ring buffer also serves topics the consumer already passes through, with no extra client-visible latency.
2. **New module `databus.py`** with endpoints in `api.py` under `/api/v1/bus/…`, matching the exact contract `databus.ts` already calls:
   - `GET /api/v1/bus/topics` — AdminClient `list_topics()` → `[{name, partitions}]`
   - `GET /api/v1/bus/topics/{topic}/messages?limit=N` — last N messages from the ring buffer (headers verbatim per the 6-header contract, payload as decoded JSON)
   - `POST /api/v1/bus/topics/{topic}/messages` — publish via the existing `BusPublisher`, validating the posted header against the ordered 6-key contract (makes the frontend's `publishMaDmp` real)
   - `GET /api/v1/bus/status` — broker reachability, per-topic buffer fill, subscriber state (feeds the "bridge online" chip)
3. **Vite proxy** — add `/bus` → `http://localhost:8090/api/v1/bus` (with rewrite) next to the existing `/ux` proxy, so `bridgeBase()`'s default `/bus` works unchanged and no `databus.ts` URL logic changes.
4. **Graceful degradation unchanged** — without/unreachable broker the endpoints answer `{"online": false}`; `TheDatabus.vue` keeps its demo-message fallback (existing behaviour). No new dependencies (`confluent-kafka` already in the socket stack).
5. **Tests** — socket-ux's established two-tier pattern: fake consumer objects / `httpx.MockTransport`, no broker needed; one `live`-marked test against the real broker.

## Acceptance Criteria
- [x] **Scenario:** Bridge exposes topics and recent messages
	- **Given:** The Kafka broker is running and `KAFKA_BOOTSTRAP_SERVERS` is configured for socket-ux
	- **When:** `GET /api/v1/bus/topics` and `GET /api/v1/bus/topics/{topic}/messages?limit=20` are called
	- **Then:** The topic list matches the broker, and each returned message carries the 6-header contract (socket_id, ontology_uri, project_id, schema_id, timestamp, lineage) plus topic/partition/offset
- [x] **Scenario:** Messages become visible in the UI
	- **Given:** The bridge is online and the frontend opens the Databus view
	- **When:** Messages exist on a topic (e.g. after a sync run publishes `project.created` on `edo.projects.v1`)
	- **Then:** `TheDatabus.vue` shows the real messages (topic chips, expandable header/payload view) instead of the demo message; without broker it stays in demo mode
- [x] **Scenario:** Publishing from the UI works
	- **Given:** The bridge is online
	- **When:** `POST /api/v1/bus/topics/{topic}/messages` receives a payload + 6-header document
	- **Then:** The message is produced to the topic and appears in the topic's recent messages
- [x] **Scenario:** Offline behaviour preserved
	- **Given:** No broker is configured or reachable
	- **When:** The frontend queries the bridge endpoints
	- **Then:** They answer `online: false` (no 500s), the UI keeps the demo fallback, and the rest of socket-ux keeps working
