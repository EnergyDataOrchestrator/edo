## Business Context
> **As a** Researcher / UI user
> **I want to** search, filter and group the databus messages semantically — by socket, schema, project, ontology term or free text
> **So that** I can answer questions like "which sockets published what for project #11?", "what changed under `madmp-lightmodel` last week?", or "which messages carry dataset/sensor metadata?" — leveraging that EDO messaging is semantic by construction

Follow-up to [[CF1-012]] (raw message inspector in the UI, CF1 domain: *access* to the bus). This card is the **CF2 domain** card (*present information in suitable form*): it turns the message stream into a searchable, groupable, ontology-aware view.

**Why "semantic" is cheap here:** the messages already carry their meaning — the frozen 6-header contract names `ontology_uri` and `schema_id`, and the payloads are maDMP / internal-format documents with `edo:`, DCAT, FOAF, SOSA URIs (JSON-LD after compaction). The search therefore operates on the semantics the bus already has.

**Scoping decision (explicit):** "semantic search" in this card = **ontology/URI-based search** — SPARQL over RDF-ified messages, facet filters, ontology-term and label matching. Vector-embedding / LLM similarity search is **out of scope** (candidate for a later card if needed).

## Plan

### Backend (socket-ux)
1. **Persist messages, not just ring-buffer them.** The CF1-012 ring buffer is volatile (≈100 messages/topic, lost on restart). For search, the bridge additionally writes each consumed message into a durable RDF store: payload JSON-LD (or, for non-JSON-LD payloads, a header + flattened-payload minimal mapping via the internal-format LinkML schema) into a dedicated Fuseki dataset `/messages`, with the 6 headers as literals (`edo:`/dcterms properties). The existing Fuseki instance hosts the dataset; no new infrastructure.
2. **Query API** — `GET /api/v1/bus/messages/search` with composable parameters, executed as SPARQL against `/messages`:
   - facets: `topic`, `socket_id`, `schema_id`, `project_id`, `since`/`until`
   - `q` free text: matches payload literals **and** ontology term labels (resolved against the ontology behind `ontology_uri`)
   - `group_by`: `project` | `socket` | `schema` | `day` — returns grouped result shape for the UI
3. **Grouping without RDF fallback:** the same query shape also works against the ring buffer (`?store=memory`) so the feature degrades gracefully when Fuseki `/messages` is not yet populated.

### Frontend (vue-frontend)
4. **Search & facets in the Databus view:** search bar + facet chips (socket, schema, topic, project) + date range; results reuse the existing expandable message panels (`TheDatabus.vue`).
5. **Grouped views:** a group-by selector (project / socket / schema / day) that restructures the result list; group headers show counts.
6. **Semantic highlight:** ontology terms/URIs found in payloads render with their human label (resolved via the ontology), so a hit on "Air temperature" highlights the SOSA/edo URI behind it.

## Acceptance Criteria
- [ ] **Scenario:** Faceted search over messages
	- **Given:** Messages from at least two sockets/projects exist in the `/messages` dataset
	- **When:** The UI queries with `socket_id=socket-rdmo` and `project_id=<project 11>`
	- **Then:** Only the matching messages are returned, with counts per facet
- [ ] **Scenario:** Semantic (ontology-aware) hit
	- **Given:** A message payload references an ontology term (e.g. an `edo:`/SOSA URI with label "Air temperature")
	- **When:** Searching `q=air temperature`
	- **Then:** The message is found via the term/label match, and the hit is highlighted with its URI in the UI
- [ ] **Scenario:** Grouped view
	- **Given:** Messages across `edo.projects.v1` and `edo.crate.v1` for one project
	- **When:** Grouping by `project`
	- **Then:** One group per project containing its messages from all topics, newest first
- [ ] **Scenario:** Graceful degradation
	- **Given:** The `/messages` dataset is empty or Fuseki is unreachable
	- **Then:** Search falls back to the in-memory ring buffer (reduced history), and the UI shows a hint instead of failing

## Technical Context & Resources
- **Origin card:** [[CF1-012]] (bridge + raw display, CF1) — this card builds on its ring buffer and endpoints; [[CF1-001]] (the bus itself).
- **Semantic material already on the bus:** 6-header contract (`regimo_core.interfaces.message`, frozen); payloads = maDMP (`madmp-lightmodel`), internal-format compact JSON-LD (`edo:` vocabulary), RO-Crate metadata.
- **Stores:** existing Fuseki (3031) gains dataset `/messages` (TDB2, config like `/projects`); ring buffer in socket-ux for the volatile layer.
- **Ontology labels:** `schema/ontology` (`regimo.ttl`, `ONTOLOGY_PATH`) — label resolution for term highlighting.
- **UI anchor:** `TheDatabus.vue` search/facet/group controls; `databus.ts` client functions (`searchMessages(topic, params)`).
- **Out of scope:** vector embeddings, LLM ranking, cross-topic graph joins beyond header fields; message *replay* (produce) belongs to CF1-012.
