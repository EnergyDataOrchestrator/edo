## Business Context
> **As a** EDO maintainer
> **I want to** have the operational infrastructure scripts as one maintainable, testable CLI module instead of loose admin scripts
> **So that** infrastructure maintenance (RDMO instance admin, fixture XMLs, plugin installation) is reproducible, programmable and consistent with the tooling conventions of the rest of EDO

This card records the **definitions that guided the implementation** of `infrastructure/scripts` (package `edo-infra`). They were given as requirements during the 2026-11-22 session and are captured here as the decision record; the implementation already exists (commits `4378110`, `b51545d`, `c36e6f7`).

---

## Definitions (the decisions that shaped `edo-infra`)

1. **Placement & scope.** Operational scripts for the infrastructure parts that live *outside* Docker belong under `infrastructure/`, next to what they operate (`Servers/rdmo-app`, `fixtures/rdmo/`, plugins) — not scattered as ad-hoc admin scripts, and not inside the domain packages (`core`, `fuseki-proto`).
2. **Module with its own CLI, not a script collection.** The loose standalone scripts were turned into **one installable Python package with a single CLI entrypoint** (`edo-infra`). One module, one help text, discoverable commands — "modify the script collection … to a python module with its own cli".
3. **House CLI pattern.** The CLI takes its inspiration from the existing CLIs of the main project (`fuseki-proto`, `regimo-core`): a **Click command group**, per-command options with **sane defaults derived from the repository layout** (`--rdmo-app` defaults to `infrastructure/Servers/rdmo-app`, `--xml`/`--xml-out` to `infrastructure/fixtures/rdmo`), **`--dry-run`/`--list` previews** for destructive or side-effecting operations, and **idempotent** behaviour (re-running is safe: `install-exporter` verifies before acting, `add-dataset` aborts on an existing dataset name).
4. **src layout.** The package uses the src layout (`src/edo_infra/`, `package-dir = { "" = "src" }`) — same packaging style as `rdmo-madmp-exporter` and the other EDO packages, so the importable code never sits on the packaging root.
5. **Runs via `uv` from the repo root.** `uv run --project infrastructure/scripts edo-infra <cmd>`; the outer CLI depends only on Python ≥ 3.10 and `click`, so it starts fast and has no heavy imports.
6. **Environment re-exec for Django commands.** Commands that must touch the RDMO database (Django ORM) **re-execute themselves under the instance environment** (`Servers/rdmo-app/env/bin/python`) instead of requiring the caller to activate it — the outer CLI stays dependency-free, the ORM work runs where Django lives.
7. **Programmability over hand-editing.** Fixture changes (e.g. adding a dataset to a project XML) must be realisable **programmatically and repeatable** — data-driven options (`add-dataset --papers CSV` with Author/Publication-Date/Title columns) instead of manual XML edits.

## Acceptance Criteria
- [x] **Scenario:** Script collection is a module with its own CLI (2026-11-23, see activity log)
	- **Given:** Standalone admin scripts under `infrastructure/scripts` (reset, DOI import, exporter install)
	- **When:** The collection is converted into the package `edo-infra` with a Click CLI
	- **Then:** `uv run --project infrastructure/scripts edo-infra --help` lists all commands from one entrypoint
- [x] **Scenario:** Package follows the house conventions
	- **Given:** Definitions 3–6 above (house CLI pattern, src layout, uv invocation, env re-exec)
	- **When:** `pyproject.toml` and `src/edo_infra/` are inspected and the commands are run
	- **Then:** src layout present, click-only outer dependency, defaults per repo layout, `--dry-run`/`--list` previews, idempotent commands, Django commands re-exec under the RDMO env
- [x] **Scenario:** Fixture additions are programmatic
	- **Given:** A fixture project XML and a papers CSV (Author, Publication Date, Title)
	- **When:** `edo-infra add-dataset --papers …` runs
	- **Then:** The dataset block (and paper rows) is added to the XML without hand-editing; re-running with the same dataset name aborts (idempotent)
